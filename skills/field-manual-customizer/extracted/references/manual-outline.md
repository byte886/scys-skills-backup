# 手册组织与步骤

先从用户要完成的事倒推必需动作。以下是写法参考，不是固定章数；例子不提供任何现行平台规则或按钮依据。

## 一、开头：目录 → 阅读说明 → 路线图 → 条件

整本手册在一级书名后空一行、第三行写 `> 手册类型：通用版` 或 `> 手册类型：定制版`；随后按以下顺序写二级标题。读者打开 PDF 依次看到：

1. **目录**：模板自动生成网页侧栏与 PDF 打印目录，排在最前。源稿**不手写**“目录”“Contents”一节，手写的会在 PDF 里重复出现一次。
2. **阅读说明**：源稿正文的第一节。集中交代作者自述数字、规则时效、不承诺结果、虚构示例和编号含义，并用一句话告诉读者先看路线图、查阅内容去附录；仅在动作会受影响时就地补具体限制。
3. **路线图**：紧接阅读说明，标题写成“30 天路线图”，或按手册周期写“4 周路线图”“上架前路线图”。按周或按阶段列出要做的事，每一步都是能点到对应章节的链接；每天的用时与产物另有日程章节时，也从这里链过去。表下另起一句“这一阶段先不做什么、以后再看什么”，链到附录对应条目；没有附录时写明不在本手册范围。路线图替代旧版“现在先做什么”一节，不再另写一遍。
4. **然后**才是下表内容：

| 内容 | 应写什么 | 检查 |
| --- | --- | --- |
| 本次结果 | 用户现在要完成的具体事 | 已有账号不能又默认从注册开始 |
| 条件 | 定制版写已知条件与“未经确认的示例条件”；通用版写“本手册按以下读者画像编写”及“条件不同时怎么调” | 不把通用读者当成某一个人 |
| 阻碍完成的缺口 | 哪一步缺什么、可以先做什么 | 在执行前可见，不只藏在附录 |

“现在做什么”“以后再看”已由路线图承担，这里不重复。用户要完整版时，以后再看的内容仍完整保留在附录。

```markdown
## 4 周路线图

| 阶段 | 本阶段怎么做 | 点开对应章节 |
| --- | --- | --- |
| 第 1 周：搭底座 | 核账号与安全设置，写好主页 | [步骤 1 账号](#section-s1) · [步骤 2 主页](#section-s2) |
| 第 2–4 周：稳定产出 | 按日程产出、回复并每周复盘 | [日程](#section-route) · [步骤 3 产出](#section-s3) · [步骤 4 复盘](#section-s4) |

这一阶段先不做：付费推广、第二个账号；以后再看[附录 C：后续变现](#section-later)。
```

上例的阶段、章节与链接均为虚构结构示意，不代表任何平台规则。

正文组织围绕实际路径。电商可能需要选方向、找货、拍图、设物流、上架；内容可能需要定位、做内容、检查发布、读反馈。顺序取决于实际前置条件：若选品中心需要先开通权限，不能机械把所有选品都放在开通前。成本和资格在首次投入前交代。

## 二、正文只留主线，查阅内容进附录

篇幅以更细更全为先，可读性靠下面的结构解决，不靠删信息，也不设页数或字数上限。

- **章首导读**：主线各章和附录各章开头写 2–3 行：这一章解决什么问题、做完之后是什么样子。阅读说明、路线图和来源节不需要。
- **主线与附录分层**：正文按动手顺序只留主线步骤。全员对照表、官方规则摘录、可套用模板、案例卡、方向依据、后续阶段等查阅型内容集中到附录（“附录 A｜方向依据”“附录 D｜可套用模板”），每个模板或案例卡有自己的锚点；正文原位置留一行可点击的跳转，如“参见[附录 D：模板 T1](#template-t1)”。
- **跨章去重**：同一段意思只在最合适的一处保留，其余位置改成跳转链接。常见重复：路线图与“现在先做什么”、步骤与附录的同一案例、几章各写一遍的同一条规则。
- **移动不等于删除**：调整结构时列出删除清单，每项写原文和去向；只删取资料的过程和跨章重复。案例卡、模板、对照表和来源标记逐项核对移动前后数量相同，复核时发现漏掉的内容补回原位置。

## 三、操作步骤的例子

```markdown
### 步骤 1 保存第一份内容草稿

**目标**：留下第一份可核对的内容草稿。

1. 准备已具备的账号或材料，核对此前步骤的产物。
2. 只按已读原文或截图支持的入口进入，并注明适用端。
3. 填写草稿，记录影响后续的选择及理由。[S1]
4. 若入口不存在，核账号类型和客户端版本；仍无依据就记缺口，不编另一条路径。

**做完的标准**：得到可再次打开的草稿，并记下待核问题；不能只写“操作完成”。

**依据**：文末 S1 给原文定位，标记可点到该条，来源条目能回到正文；同一句多来源合为一个标记组。图注说明真实图证明哪个动作、来源、日期和边界；原创图仅解释已核实规则，虚构样例仅展示结构。
```

不要求没有表单的步骤硬写“填什么”。步骤编号用“步骤 1”等；站内来源才用 S1。相同编号可用于 `plan.md` 和 `review.json`。旧 `S1` 步骤标题需要迁移，文件检查会给明确失败提示。写作前在 `plan.md` 对每个关键动作选真实截图、原创示意、虚构样例或纯文字，并说明选择理由；选文字时说明为何足够。没有截图不等于不需教学图；路径本身缺依据时标明部分完成，不能靠画一张猜测界面补齐。

每步用一句话目标、3–5 条动作清单和做完的标准；长段拆短。真实手册中的案例卡写起点、做法、作者自述结果和来源，放在附录；可用案例少就用实际数量。已读材料里的反复做法要进入步骤，能直接套用的模板须用明确虚构的占位，同样放附录、步骤里留跳转。示例中的 `[S1]` 在成稿中必须转成可点的来源锚点，不能保持纯文本。

## 四、判断步骤的例子

```markdown
### 步骤 2 选出这次要写的主题

**目标**：选出一个有依据、适合目标读者的主题。

1. 收集已知用户问题、资料和实际观察，列为判断输入。
2. 对照来源标记与适用条件写判断理由；助手的推断标为建议。
3. 用一个看似热闹但不符合目标读者的主题检验判断，记下反例。
4. 选定主题并写下一步：证据足够就做草稿，不足就先补哪项。

**做完的标准**：留下主题、理由、反例及待核问题，可观察下一步是否能启动。
```

诊断不能只复述他人的结论。“搜索里没找到”是观察；是否限流及原因需要另外判断。不得把相关性直接写成确定原因。

## 五、进度与附录

进度表写时间安排、动作、预计总时长、完成结果、依据或假设。准备、阅读、制作和回复均计入总时长。用户只在晚上有空，就不能直接照搬作者早上发布并即时回复的日程；确有必要时说明冲突及可选安排。

附录保存查阅型内容（见第二节）、详细规则摘录和仍需核对的问题；来源节放在最后。未知可以是零；不为填表制造未知。规则发生变化时，同时更新受影响步骤、旧截图提示及日程。更换个人条件时，仅调整受影响的部分，并列出改动。

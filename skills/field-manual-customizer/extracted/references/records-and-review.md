# 记录、复用与核对

这是工作目录里的内部记录。交付手册时不把整份原始缓存重复放进正文，也不把含签名链接或用户资料的缓存打包进公开技能。

## 一、保存什么

| 文件 | 内容 | 更新方式 |
| --- | --- | --- |
| plan.md | 写作视角、用户目标或通用读者画像、已知条件与假设；从目标倒推的必需动作、前置条件、配图选择；素材总结性做法采用或舍弃的理由 | 检索前先列，写作前补配图和素材覆盖计划；无图时写文字为什么足够，不为数量凑图 |
| sources.md | 稳定 ID 或原文 URL、标题、作者、发布日期、取得时间、取得方式（现行页面，或存档链接与快照日期）、原始文件、使用章节；全文/摘要/未读；可用案例、总结性做法、可改成模板的结构及不可用原因 | 同一来源只存一份，按稳定 ID 去重；来源编号对应正文锚点与文末回链 |
| rules.md | 每条规则的原文、适用范围、发布时间、生效时间、查询时间、读的是现行页面还是存档（快照日期）、证据类别、来源定位、影响步骤、结论及未知部分 | 更新时同时改正文、图注和进度；没有规则或未知写无，不凑条数 |
| _raw/ | 实际取得的原始返回、正文或官方摘要，保留完整性说明 | 能直接存返回就存；客户端未存文件时，可从工具调用记录原样导出完整返回，标注导出方式、工具和时间；人工摘录明确标为摘录，不伪造原始响应 |
| images/ | 用到的图片及其来源关系；原创示意图的 SVG 源与 PNG 成品 | 成功下载后复用，不重复下载；示意图修改源后重新转 PNG 并核对图注 |
| review.json | 针对当前稿的内容核对记录和真实试用情况 | 正文变更后旧核对失效，完成核对再更新摘要哈希 |
| changes.md | 旧内容、新内容、修改原因、新依据、受影响章节 | 仅调整或更新任务需要 |
| run_notes.md | 实际各阶段耗时、接口调用、重用/新增来源、失败与重试（如某站拒绝程序访问后改读存档；这类过程只写这里和来源节，不进读者正文） | 无法取得的统计写未知，不把 total_tokens 当实际费用 |

缓存按用户及其权限范围隔离。含签名链接的 `_raw/`、`images/` 和图片映射只放当前用户的私有工作目录；在可控制权限的系统上设目录仅本人可读写（如 `chmod 700 <工作目录>`），不放共享目录。链接失效或任务结束后按用户授权的保留期限清理缓存；清理前先确认仍需用于来源核对的证据。公开交付或打包前逐项检查 `_raw/`、`images/`、`*_map.json` 未误带入，网页里只放允许交付的图片与最小来源定位。重用规则前核是否过期；更新任务重新查用户指定时间内的变化。请求失败最多再试两次；限流按服务端等待。停止后保留已完成位置，下次只补缺口。

`plan.md` 配图计划沿用现有动作 ID，可写表格：`动作 ID｜要解释的内容｜真实截图/原创示意/虚构样例/纯文字｜依据或来源｜选择理由/文字足够的理由`。图的数量由动作需要决定。`review.json` 现有 `checks[id=images].evidence` 记录逐图内容、清晰度、图注来源/日期/适用边界、网页放大及 PDF 同页核对；若 0 图，记录人工复核纯文字可读性的具体结果，不能把脚本警告消失当作已试读。

`plan.md` 还需列出主素材有效内容及采用情况：代表性案例、反复出现的做法、可套用模板、舍弃理由。材料充足时通常选 6–8 个代表性案例，不足则用实际可用数量；不能为凑数编造。`review.json` 的 `checks[id=scope].evidence` 记录视角、案例与总结性做法的覆盖、模板占位、正文与主素材有效信息量的对照，以及开头顺序、路线图链接、主线与附录分工和删除清单（只删取资料过程与跨章重复，移动内容数量不变）；`checks[id=rules].evidence` 记录来源标记与证据性质，`checks[id=route].evidence` 记录步骤清单和完成标准。机械文件检查不能替代这些语义核对。

## 二、review.json 的最小形状

先把 plan.md 里的必需动作带入 `steps`，再写正文；不能从已经写出的章节反推检查范围。每次内容核对针对当前稿，摘要可用：

```bash
python3 -c "from pathlib import Path; import hashlib; print(hashlib.sha256(Path('手册.md').read_bytes()).hexdigest())"
```

下面是字段示意，尖括号必须换成实值。它不是通过的范例。

```json
{
  "schema_version": 1,
  "skill_version": "0.10.1",
  "manual_sha256": "<当前正文 SHA-256>",
  "reviewer": "<谁进行了内容核对>",
  "reviewed_at": "<ISO 日期或时间>",
  "goal": "<本次用户想完成什么>",
  "steps": [
    {
      "id": "步骤1",
      "title": "<必需动作>",
      "critical": true,
      "section": "<正文中不带井号的完整标题>",
      "status": "gap",
      "evidence": [],
      "note": "<缺什么、阻碍什么、怎样核对>"
    }
  ],
  "checks": [
    {
      "id": "route",
      "status": "not_reviewed",
      "evidence": "<对照用户请求和正文的具体结果>"
    }
  ],
  "usability": {
    "status": "not_tested",
    "scope": "",
    "evidence": []
  }
}
```

`steps[].status` 用 `supported`、`gap`、`not_applicable`。有缺口就写 gap，给具体理由；不适用要解释，不能用它绕过目标所需动作。supported 要有正文对应标题、note，以及原文证据数组，每项为 `{"path":"_raw/source.md","locator":"具体段落或行","sha256":"原文文件 SHA-256"}`。这些证据必须实际读取；摘要不能支持未显示的完整点击路径。

`checks` 逐项包含 `route`、`rules`、`numbers`、`images`、`schedule`、`scope`。每项 status 用 `pass`、`fail` 或 `not_reviewed`，evidence 写具体结果。该项目不适用时仍说明为什么，不编造检查。关键动作覆盖由 steps 单独记录。没有图片、平台规则或未知项也可以通过，但 `images` 须说明对应的配图计划与人工可读性复核依据，尤其是零基础手册 0 图时。

`usability.status` 用 `not_tested`、`passed` 或 `failed`。实际试用必须写 scope，并用与上面相同的证据结构指向试用记录。记录谁在什么环境做了哪些动作、实际结果和卡点；助手推演、结构检查不能记成真实用户试用。

评分工具只能校验这份记录的结构、正文版本、证据文件及摘要是否一致，不能机械证明其内容判断正确。因此输出称为“内容核对记录完整”或“有内容缺口”，仍需读原文判断。真实会员权限和真实新手试用必须另做，模拟不冒充真实。

## 三、更新时只改受影响部分

先保存旧稿，再对照个人条件或规则变化找到依赖它的步骤。复用仍有效的来源与图片，必要时补读；修改正文、图注、进度和来源说明，并重核受影响的步骤。未受影响部分可沿用原核对依据，说明沿用范围；正文哈希重新生成，但不把旧证据日期改成今天。

局部更新没有新规则或图片时，不强制凑这些产物。检查旧版所有受影响引用，确保旧门槛没有残留在目录、例子或进度中。记录改了什么及未改动的范围即可，不默认重写整本。
